## 一、包管理工具发展总览

| 时间 | 事件 | 关键里程碑 |
|------|------|-----------|
| 2010 年 | npm 诞生 | 随 Node.js 推出，成为 Node.js 生态标准包管理器 |
| npm v1/v2 | 嵌套结构依赖 | 完全按目录结构下载依赖树，造成依赖黑洞 |
| 2016 年 | yarn 发布 | 由 Facebook、Google、Exponent、Tilde 联合开发，解决 npm v3 时期的诸多缺陷 |
| npm v3 | 扁平化结构 | 引入 hoist 机制，将子依赖提升到根目录 |
| npm v5 | package-lock.json | 参考 yarn 的 lock 思路，锁定依赖版本 |
| 2017 年 | pnpm 发布 | 基于内容寻址存储 + 软硬链接，解决幽灵依赖、磁盘空间、安装速度等问题 |

## 二、npm 详解

**2.1 npm 三大模块**

npm 功能强大，主要分为三大部分：

1. **网站**：npm 包发布和查找的网站，可搜索各种满足需求的包。
2. **注册表（registry）**：一个巨大的数据库，保存了每个 package 的信息。例如 `https://registry.npmjs.org/react`。
3. **命令行工具（CLI）**：开发者使用的命令行工具，进行包的安装、发布等操作。安装 Node.js 时自动附带，无需单独安装。

**2.2 npm 进化史**

**阶段一：嵌套结构依赖（npm v1/v2）**

最早期的 npm 采用最直接的嵌套式结构管理 `node_modules`：项目依赖 A、B、C 包，它们各自又依赖 package D，那么 D 会被重复安装多次。

```
node_modules
 ├── moduleA
 │   └── node_modules
 │       └── moduleC
 └── moduleB
     └── node_modules
         └── moduleC
             └── node_modules
                 └── moduleD
```

**存在的问题：**

- **重复依赖安装**：同一依赖被多个包依赖时，会被下载多次。
- **层级依赖过深**：如果 package D 还依赖其他包，会一直嵌套下去，导致体积变大。
- **Windows 路径过长**：Windows 上文件路径最长支持 260 多个字符，深层嵌套会导致安装脚本报错，甚至无法用常规方法删除 node_modules。
- **缓存能力差**：无离线模式。
- **版本管理不稳定**。

**阶段二：扁平化（npm v3）**

npm v3 针对上述问题采取了**扁平化（hoist 机制）**解决方案：

- 按照安装顺序，如果遇到相同版本的依赖，会将其提升到顶层 `node_modules`。
- 安装相同模块时，根据 Node 的 require 机制，会逐级往上寻找 `node_modules`，判断已安装的模块版本是否符合新模块的版本范围：符合则跳过，不符合则在当前模块的 `node_modules` 下安装该模块。

```
node_modules
 ├── moduleA
 ├── moduleB
 ├── moduleC
 └── moduleD
```

**扁平化衍生的三大问题：**

1. **幽灵依赖（Phantom Dependencies）**
   - 指在 `package.json` 中未声明，但因为被其他包依赖而被安装到 `node_modules` 根目录的包。
   - 例如 package D 1.0 还依赖了 package H，那么 package H 并没有在 `package.json` 中引用，但项目中可以直接使用。
   - **危害**：可能导致依赖丢失、版本兼容差异、环境不一致、代码可读性和可维护性降低。

2. **依赖分身（Dependency Duplication / 双胞胎陌生人）**
   - 同一依赖的不同版本（如 package D 1.0 和 package D 2.0），因为版本不一致无法都提升到顶层，其中一个仍保留在子包的 `node_modules` 下，导致重复安装。
   - **危害**：
     - 仍然出现重复包依赖安装，增加 node_modules 体积；
     - 无法共享库实例，引用得到的是两个独立的实例；
     - 如果其中有 TypeScript 声明文件，会导致使用混乱，编译器报错。

3. **依赖不幂等**
   - 多次执行相同的安装命令，可能得到不同的结果（因为 hoist 哪个版本取决于安装顺序）。
   - 两个依赖包同时依赖 C 包的不同版本，C 包只有一个版本会被 hoist，到底提升哪个版本是不确定的。

**阶段三：lock 诞生（npm v5）**

npm v5 参考 yarn 的思路，引入了 `package-lock.json` 锁文件，解决依赖不幂等的问题。通过 lockfile 锁定安装版本，使得每次执行 `npm install` 时依赖版本都相同。

> 注：在 package-lock.json 出现之前，可以通过 `npm-shrinkwrap` 实现锁定依赖结构，但默认关闭，需要主动执行。

**2.3 package-lock.json 字段详解**

```json
"yargs": {
  "version": "16.2.0",
  "resolved": "https://registry-npm.myscrm.cn/repository/pkg/yargs/-/yargs-16.2.0.tgz",
  "integrity": "sha512-D1mvvtDG0L5ft/jGWkLpG1+m0eQxOfaBvTNELraWj22wSVUMWxZUvYgJYcKh6jGGIkJFhH4IZPQhR4TKpc8mBw==",
  "dev": true,
  "requires": {
    "cliui": "^7.0.2",
    "escalade": "^3.1.1"
  },
  "dependencies": {
    "is-fullwidth-code-point": {
      "version": "3.0.0",
      "resolved": "...",
      "integrity": "...",
      "dev": true
    }
  }
}
```

| 字段 | 说明 |
|------|------|
| `version` | 唯一版本号 |
| `resolved` | 包的安装源（下载地址） |
| `integrity` | 用于验证包完整性的 hash 值，格式为 `加密hash函数-摘要digest`。加密函数有 `sha512` 或 `sha1`，digest = base64(hashfn(content)) |
| `dev` | 是否为开发时依赖项 |
| `requires` | 当前包的 `dependencies` 依赖项 |
| `dependencies` | 当前包的 `node_modules` 依赖树（某个子依赖包存在多版本时，当前包下生成的 node_modules 结构） |

> lock 文件解决了依赖不幂等问题，但扁平化的幽灵依赖等本质问题并未解决。

**2.4 npm init**

执行 `npm init` 会初始化一个 `package.json` 文件，核心字段：

| 字段 | 说明 |
|------|------|
| `name` | 包的名称 |
| `version` | 包的版本信息 |
| `description` | 包的描述信息 |
| `main` | 包的入口文件 |
| `scripts` | 包的脚本命令 |
| `author` | 作者 |
| `license` | 开源声明 |

**2.5 npm install 完整流程**

```
npm install → 检查config配置 → 有无lock文件？
                              ├─ 有 → 对比package.json与lock是否一致 → 一致则从lock获取版本构建依赖树
                              │                                  → 不一致则按扁平化递归生成依赖树
                              └─ 无 → 构建依赖关系 → npm仓库registry → 拉取压缩包 → 根据依赖结构生成node_modules → 安装完毕
                                                                   → 有缓存 → 使用缓存的压缩包
```

**详细步骤：**

1. **检查 npm config 配置**
   - 读取 `.npmrc` 配置文件（npm 运行配置文件）。
   - 查看配置命令：
     ```bash
     npm config list    # 查看主要配置信息
     npm config ls -l   # 查看所有配置信息
     ```
   - 配置文件按优先级从高到低读取（高优先级覆盖低优先级）：
     1. **项目级别** `.npmrc`：项目根目录下创建，只用于管理当前项目。
     2. **用户级别** `.npmrc`：当前登录用户的配置，通过 `npm config get userconfig` 获取位置。
     3. **全局级别** `.npmrc`：一台电脑多用户共享的公共配置，通过 `npm config get prefix` 获取。
     4. **npm 内置** `.npmrc`：`/path/to/npm/npmrc`。

2. **读取 package.json，检查 package-lock.json**
   - 如果存在 lock 文件，将 `package.json` 声明的依赖与锁文件对比：
     - 一致 → 从锁文件获取版本信息，构建依赖树。
     - 不一致 → 按扁平化处理，递归生成依赖树。

3. **缓存机制**
   - 安装依赖时，除了放到 `node_modules`，还会在本地缓存目录缓存一份。
   - 缓存目录通过 `npm config get cache` 获取。
   - 再次安装时，根据 `package-lock.json` 中的 `integrity`、`version`、`name` 生成唯一 key，用 key 查找缓存记录。找到缓存后，根据 tar 包的 hash 值找到缓存的压缩包，解压到项目 `node_modules`，省去网络下载开销。

**2.6 npm run 运行原理**

`npm run` 的核心功能是执行 `package.json` 中 `scripts` 字段定义的脚本。

**运行流程：**

```
npm run "script name"
  → package.json 中查找 script 命令
    ├─ 不存在 → "script not found" 报错
    └─ 存在 → 查找 node_modules/.bin 目录下是否存在该执行脚本
                ├─ 存在 → 执行
                └─ 不存在 → 查找全局 node_modules 的 bin
                            ├─ 存在 → 执行
                            └─ 不存在 → 查找 PATH 环境变量中其他同名可执行程序
                                        ├─ 存在 → 执行
                                        └─ 不存在 → 报错
```

**.bin 目录原理：**

- 安装依赖时，npm 会在 `node_modules/.bin` 目录中创建以依赖名为名的可执行文件（软链接）。
- 一个同名依赖通常有三个执行文件：`index.js` 执行文件、Windows 的 `.cmd` 执行文件、类 Unix 的 shell 执行文件，根据系统环境执行对应脚本。
- 可执行文件开头用 `#! /usr/bin/env node` 指定解释器。
- 依赖包的 `package.json` 中通过 `bin` 字段声明可执行文件映射，例如：
  ```json
  "bin": {
    "taro": "bin/taro"
  }
  ```
- npm 读到该配置后，将该文件软链接到 `./node_modules/.bin` 目录下。
- npm 还会自动把 `node_modules/.bin` 加入 `$PATH`，因此可以直接作为命令运行依赖程序，无需全局安装。

> 总结：npm install 时帮我们配置好软链接（相当于一种映射），执行 `npm run xxx` 时，到 `node_modules/.bin` 找到对应映射文件，再找到对应 JS 文件执行。

## 三、yarn 详解

**3.1 yarn 诞生背景**

yarn 诞生于 npm 处于 v3 的时期（2016 年），当时 npm 还没有 `package-lock.json`，存在以下问题：

- 重复依赖安装
- 层级依赖过深，体积变大
- 缓存能力差，无离线模式
- 版本管理不稳定

yarn 的出现很好地解决了这些问题，后期 npm 也参考了 yarn 的 lock 文件方案。


**3.2 yarn 核心特点**

1. **模块扁平化**：将不同版本的依赖包按一定策略归纳版本，避免重复安装。
2. **缓存机制**：实现离线模式，解决缓存能力问题。
3. **锁文件**：`yarn.lock` 锁定依赖版本，即使不同安装顺序，相同依赖关系在任何环境和容器中都能以相同方式安装。
4. **网络性能更好**：
   - 采用请求排队理念（类似并发池连接），更好利用网络资源。
   - 最大并行发送 8 个请求。
   - 以 `urlToPromise` 形式做 cache，避免向同一 URL 重复发送请求。
   - 自动重发策略：请求失败尝试重发，单请求重发上限为 5 次。
5. **更好的安全性**：检查安装的每个包的许可证，提供机制限制或拒绝具有不安全许可证的包。

**3.3 yarn.lock vs package-lock.json**

| 对比项 | yarn.lock | package-lock.json |
|--------|-----------|-------------------|
| 格式 | 自定义标记方式（YAML 风格） | JSON 结构 |
| 结尾 | `.lock` | `.json` |

**3.4 yarn install 五阶段流程**

```
检查(check)配置信息 → Resolving packages(解析包) → Fetching packages(拉取包) → Linking dependencies(连接依赖) → Building fresh packages(构建安装)
```

**阶段详解：**

1. **检查配置信息**：检查 lockfile 文件等配置信息，以及运行环境是否符合条件。

2. **Resolving packages（解析包）**：进行依赖整合。
   - **首层依赖**：收集项目 `package.json` 中定义的 `dependencies`、`devDependencies`、`optionalDependencies`。
   - **遍历所有依赖**：从首层依赖出发，递归查找每个依赖下嵌套依赖的版本信息，解析过的包通过 `Set` 数据结构存储。
   - 有 lock 文件 → 从 lock 文件获取版本信息并标记已解析。
   - 无 lock 文件 → 向 registry 发起请求获取满足版本范围的包信息，获取后标记已解析。

3. **Fetching packages（拉取包）**：
   - 检查缓存中是否有当前依赖包，将缓存中不存在的包下载到缓存目录。
   - 缓存目录通过 `yarn cache dir` 查询。
   - 缓存条目以 `{slug}/node_modules/{packageName}` 命名的目录形式保存，slug 由版本、哈希值、uid 构成，以同级平铺形式存放。
   - 拉取流程：创建缓存目录 → 解析地址下载 → 判断是否本地资源 → 是则从本地资源拉取到 node_modules；否则从 registry 拉取对应资源 → 写入缓存。

4. **Linking dependencies（连接依赖）**：将下载的依赖复制到 node_modules 下，期间做三件事：
   - 处理 `peerDependencies`：一般用在要分发的包中，当一个包必须以另一个包作为地基时使用（如 react 需要依托 react-dom、koa 插件需要依托 koa）。
   - **扁平化依赖树（dedupe）**：分析同一依赖包不同版本的使用频率，选择利用率最大的版本放置在顶层。
   - 拷贝依赖到 node_modules 下（分为从 registry 拉取的和从缓存中的包）。

5. **Building fresh packages（构建安装）**：
   - 执行 install 相关的生命周期钩子，如 `preinstall`、`postinstall` 等。
   - 依赖包中存在二进制包需要编译的，也在这一步进行。

**3.5 yarn 基础命令**

| 命令 | 说明 |
|------|------|
| `yarn init` | 初始化项目 |
| `yarn add packageName` | 安装依赖 |
| `yarn add packageName --dev` | 安装到 devDependencies |
| `yarn remove packageName` | 移除依赖包 |
| `yarn upgrade packageName` | 更新指定依赖包 |
| `yarn global add packageName` | 全局安装依赖包 |
| `yarn config get key` | 查看配置 key 的值 |
| `yarn config set key value` | 设置配置项 |
| `yarn list` | 查询所有依赖 |
| `yarn info packageName` | 查看依赖包信息 |
| `yarn config list` | 获取配置信息 |

**3.6 yarn PnP（Plug'n'Play）**

yarn 有独特的 PnP 安装方式，可以直接去掉 `node_modules`，将依赖包内容写在磁盘，节省 Node 文件 I/O 开销，提升安装速度。

> 注意：yarn PnP 和 pnpm 机制不同，总体来说安装速度 pnpm 快于 yarn PnP。

## 四、pnpm 详解

**4.1 pnpm 概述**

pnpm（performant npm）官网定位：**"快速的，节省磁盘空间的包管理工具"**（Fast, disk space efficient package manager）。

pnpm 于 2017 年发布，解决了 npm、yarn 长期存在的性能、安全访问等问题。

**官网列举的四大标志性特点：**

| 特点 | 说明 |
|------|------|
| **快速** | pnpm 比 npm 速度快 2 倍 |
| **高效** | node_modules 中的文件为复制或链接自特定的内容寻址存储库 |
| **支持 monorepos** | pnpm 内置支持单仓多包 |
| **严格** | pnpm 默认创建非平铺的 node_modules，代码无法访问任意包 |

**4.2 核心概念：硬链接与软链接**

在理解 pnpm 机制前，先了解文件系统的两种链接方式：

**硬链接（Hard Link）**

- **概念**：通过索引节点（inode）进行连接。Linux 文件系统中，保存在磁盘分区中的文件都有一个编号，称为索引节点号（Inode Index）。多个文件名指向同一索引节点的连接就是硬连接。
- **特点**：
  - 创建硬链接时，创建一个和原始文件相同的入口点，但不占用额外磁盘空间，共享相同数据块。
  - 任何一个文件的修改都会反映在另一个上。
  - **不能跨文件系统**创建，也**不能用于链接目录**。
  - 原始文件被删除后，硬链接依然可以访问数据（因为引用的是物理数据而非文件路径）。
- **使用场景**：在不同位置访问同一个文件内容而不占用额外磁盘空间，如多项目共享相同库文件。
- **创建命令**：`ln 源文件 目标文件`

**软链接 / 符号链接（Symbolic Link）**

- **概念**：一个特殊类型的文件，包含另一个文件的路径，类似于 Windows 的快捷方式。
- **特点**：
  - 软链接有自己的 inode，引用的是原文件的 path。
  - **可以指向目录**，也**可以跨文件系统**。
  - 原始文件被移动或删除后，软链接失效（悬空链接）。
- **使用场景**：需要引用特定位置的文件或目录，特别是当这些文件可能移动或变化时。
- **创建命令**：`ln -s 源文件 目标文件`

| 对比项 | 硬链接 | 软链接 |
|--------|--------|--------|
| 引用对象 | 文件的物理索引（inode） | 原文件的路径（path） |
| 额外磁盘空间 | 不占用 | 占用（存储路径信息） |
| 跨文件系统 | 不支持 | 支持 |
| 链接目录 | 不支持 | 支持 |
| 原文件删除后 | 仍可访问数据 | 失效（悬空链接） |
| inode | 与原文件相同 | 有自己独立的 inode |

**4.3 pnpm 的核心机制：Store + Link**

**Content-Addressable Store（CAS，内容寻址存储）**

- 是一种根据内容进行检索信息的存储方式，而非根据文件名寻址。
- pnpm 默认将所有依赖包下载到系统 `{home dir}/Library/pnpm/store/v3` 中。
- 系统中相同文件只会存在一份。
- 基于内容寻址的好处：即便包版本升级了，也仅需存储改动 Diff，而不需要存储新版本的完整文件内容，进一步节约存储空间。
- CAS 目录结构：
  ```
  ~/pnpm/store
  └── v3
      └── files
          ├── 00
          │   ├── 0b12x..
          │   └── e0b21..
          └── 01
  ```

**Virtual Store（虚拟存储）**

- 指向存储的链接的目录，所有直接和间接依赖项都链接到此目录中。
- 对应项目中的 `node_modules/.pnpm` 目录。

**硬链接的应用**

- `pnpm install` 时先看 Store 中是否存在该文件。
- 如果存在，则在 `.pnpm` 下创建该文件的硬链接（hard link）到 Store 中对应的文件，而不是重新下载。
- 不同项目中相同的包无需重复下载，极大节省磁盘空间，提升下载速度。

**软链接的应用**

- 项目中依赖包以及子依赖包通过软链接方式联系起来。
- 所有软链都是从 `.pnpm/<package-name>@<version>/node_modules/<package-name>` 目录下链接过来。

**4.4 pnpm 的 node_modules 结构**

```
node_modules
├── .pnpm
│   ├── foo@1.0.0
│   │   └── node_modules
│   │       ├── foo     → 硬链接到 store
│   │       └── bar     → 软链接到 ../../bar@1.0.0/node_modules/bar
│   ├── foo@2.0.0
│   │   └── node_modules
│   │       └── foo
│   └── bar@1.0.0
│       └── node_modules
│           └── bar
├── react       → 软链接到 .pnpm/react@x.x.x/node_modules/react
├── eslint      → 软链接到 .pnpm/eslint@x.x.x/node_modules/eslint
└── .bin
```

**关键特点：**

- 只有项目中**真正依赖的包**（直接依赖），才会出现在 `node_modules` 根目录下，且都是软链接。
- 其他所有子依赖，以 `<package-name>@<version>` 的方式平铺在 `.pnpm` 目录下。
- `.pnpm` 下每个包的每个文件都是来自内容可寻址存储的硬链接。
- **没有依赖提升（hoist）的概念，因此没有幽灵依赖问题。**

**软链接示例说明：**

- 项目依赖 A → 在 `node_modules` 根目录创建 A 软链，指向 `node_modules/.pnpm/A@1.0.0/node_modules/A`。
- A 依赖 B → pnpm 把 B 放置在 `.pnpm` 中，A 通过软链接依赖到 B，避免嵌套过深。

**4.5 pnpm install 三阶段**

```
Resolving(依赖解析) → Fetching(目录结构计算/下载) → Linking(链接依赖项)
```

1. **依赖解析（resolving）**：解析依赖树，决定要下载哪些安装包，仓库中没有的依赖都被识别并获取。
2. **目录结构计算（fetching）**：下载依赖的 tar 包，可同时下载多个以增加速度。
3. **链接依赖项（linking）**：解压包，根据文件构建出真正的依赖树，需要大量文件 I/O 操作。使用符号链接技术和并行安装，显著提高安装速度。

**4.6 传统安装 vs pnpm 并行安装**

**传统安装（npm/yarn）：**

- 三个阶段线性执行：所有包先一起 Resolving → 所有包一起 Fetching → 所有包一起 Writing。
- 虽然 Fetching 阶段支持并行下载，但整体是批量串行的。

**pnpm 安装：**

- 每个包独立并行执行三个阶段：一旦一个包被解析，就开始下载；下载完毕后立即开始写入。
- 额外增加 **Linking（链接）** 步骤：写入完成后创建硬链接和符号链接，形成项目的 node_modules 目录结构。
- 链接过程很快，因为避免了复制文件的开销。
- 多项目和 Monorepo 环境下优势尤其明显。

**4.7 pnpm 高效性详解**

- **节省磁盘空间**：使用 npm 时，依赖每次被不同项目使用都会重新安装一次。pnpm 中依赖存储在内容可寻址存储中，多个项目共享同一版本依赖。
- **增量更新**：如果有多个不同版本的依赖包，发现某个版本更新有修改，`pnpm update` 只需添加修改的文件到存储中。
- **官方原话**：所有文件都会存储在硬盘上的某一位置。当软件包被安装时，包里的文件会硬链接到这一位置，而不会占用额外的磁盘空间。这允许跨项目地共享同一版本的依赖。

**4.8 pnpm 严格性详解**

- yarn 和 npm 通过扁平化处理，将依赖包提升到根结构，源码可以直接访问和修改依赖，而不是作为只读的项目依赖。
- pnpm 使用符号链接将项目的**直接依赖项**添加到模块目录根目录中。
- 默认情况下不允许访问未声明的依赖（非扁平结构）。

**4.9 pnpm 基本命令**

| 命令 | 说明 |
|------|------|
| `pnpm add packageName` | 安装包 |
| `pnpm add -D packageName` | 安装为 devDependencies |

- **MultiRepo**：每个包一个独立仓库，多个仓库分散管理。
- **MonoRepo**：多个包放在同一个仓库中，统一管理。

```bash
pnpm --filter basic-components i -D @babel/preset-env
```

前提是子包声明了 `package.json`，且 `name` 为 `basic-components`。

## 六、核心概念深度解析

**6.1 幽灵依赖产生的根本原因**

即使使用 pnpm，幽灵依赖也难以完全根除，原因有三：

1. **包管理工具的依赖解析机制**
   - 扁平化（hoist）机制将子依赖提升到根目录，导致未声明的依赖可被直接引用。

2. **第三方库历史问题**
   - 由于历史原因或开发者疏忽，有些项目没有正确声明所有直接使用的依赖。
   - 对于三方依赖，幽灵依赖已被当做默认功能使用，提 issue 修复周期很长。
   - pnpm 对此只能做出妥协。

3. **JavaScript 模块解析策略**
   - Node.js 的模块解析策略允许从当前文件夹的 `node_modules` 开始，向上遍历文件系统直到找到所需模块。
   - 这种灵活性使得幽灵依赖更容易产生。

**6.2 pnpm 对幽灵依赖的妥协处理**

- **对直接依赖严格管理**：确保项目只能访问 `package.json` 中声明的依赖。
- **对间接依赖妥协处理**：默认启用 `hoist` 配置，将一些间接依赖提升到特殊目录 `node_modules/.pnpm/node_modules` 中，在保持依赖隔离的同时允许某些特殊情况下的间接依赖被访问。

> 综合来看，幽灵依赖目前无法根除，只能通过额外处理进行管控，如 eslint 对幽灵依赖的检查规则、pnpm 的 hoist 配置等。

**6.3 peerDependencies（对等依赖）**

- `peerDependencies` 一般用在要分发的包中，当一个包必须以另一个包作为"地基"时适合使用。
- 例如：react 需要依托 react-dom、koa 插件需要依托 koa。
- `--save-peer` 安装为 peerDependencies，同时安装到 devDependencies。
- npm 3 中不会再强制安装 peerDependencies 中指定的包，而是通过警告提示。

## 八、从 npm/yarn 迁移到 pnpm

**8.1 迁移前的核心障碍**

使用 npm 或 yarn 安装依赖时，所有包都被提升到模块目录根目录，源代码可以访问未作为依赖项添加到项目的依赖项（幽灵依赖）。但 pnpm 默认使用链接仅将项目的**直接依赖**添加到模块目录根目录，这意味着 `package.json` 没有引用的依赖将无法解析。这是迁移中的最大障碍。

**8.2 迁移步骤**

1. **使用 npkill 删除 node_modules**
   - `npkill` 工具可以列出系统中任何 node_modules 目录及其占用空间，然后选择删除以释放空间。
   - 对于多个使用 npm 安装依赖的项目，单独删除很耗时间，npkill 非常实用。

2. **全局安装 pnpm**
   ```bash
   npm i -g pnpm
   ```

3. **项目根目录创建 `.npmrc`**
   ```
   auto-install-peers=true
   ```
   > `auto-install-peers` 默认为 false，设置为 true 可自动安装 peer 依赖。

4. **导入依赖锁定文件**
   - 保证根目录有如下依赖锁定文件之一：`npm-shrinkwrap.json`、`package-lock.json`、`yarn.lock`。
   - 执行导入：
     ```bash
     pnpm import pnpm-lock.yaml
     ```

5. **执行安装**
   ```bash
   pnpm i
   ```

**8.3 迁移中常见问题及解决方案**

**问题一：peer dependencies 警告**

生成 `pnpm-lock.yaml` 时可能出现：

```
WARN  Issues with peer dependencies found.
└─┬ vuepress 1.9.9
  └─┬ @vuepress/core 1.9.9
    └─┬ vue-loader 15.10.1
      └─┬ @vue/component-compiler-utils 3.3.0
        └─┬ consolidate 0.15.1
          ├── ✕ unmet peer react-dom@^16.13.1: found 15.7.0
          └── ✕ unmet peer react@^16.13.1: found 15.7.0
```

**原因**：pnpm 会在全局缓存已下载过的依赖包，如果全局缓存版本与项目 `package.json` 指定版本不一致，就会出现这种警告。

**解决方案：**

方案 A：在 `package.json` 中配置 `peerDependencyRules` 忽略对应警告：

```json
{
  "pnpm": {
    "peerDependencyRules": {
      "ignoreMissing": ["react"]
    }
  }
}
```

方案 B：在 `.npmrc` 中关闭严格的对等依赖模式：

```
strict-peer-dependencies=false
```

或执行命令：

```bash
npm config set strict-peer-dependencies=false
```

> 另外可能出现 `deprecated subdependencies found` 警告，暂时可以忽略。

**问题二：幽灵依赖问题**

切换为 pnpm 后，默认不允许访问未声明的依赖。

**解决方案一（推荐）：自行安装未声明依赖项**

- 使用幽灵依赖自动扫描工具 `@sugarat/ghost`。
- 或直接手动安装：`pnpm i -S viewerjs`。
- 某些版本 pnpm 会自动爆出幽灵依赖错误 `missing peer ...`，直接安装后面的依赖即可。

**解决方案二（不推荐）：依赖提升**

在 `.npmrc` 中配置 `public-hoist-pattern` 或 `shamefully-hoist`，将依赖提升到根 node_modules：

```ini
# 提升含有 eslint(模糊匹配)、prettier(模糊匹配)、viewerjs(精确匹配) 的依赖包
public-hoist-pattern[]=*eslint*
public-hoist-pattern[]=*prettier*
public-hoist-pattern[]=viewerjs

# 提升所有依赖到根 node_modules（相当于 public-hoist-pattern[]=*）
shamefully-hoist=true
```

> **极不推荐**使用这种方式，因为没有充分利用 pnpm 依赖访问安全性的优势，又走回了 npm/yarn 的老路。

## 九、pnpm 依赖治理最佳实践

依赖治理主要涉及三个部分：

- **冗余依赖治理**：某些包可能用不到但还保留着，导致 package.json 愈发混乱。
- **重叠依赖治理**：monorepo 中常见，如根目录与子项目声明了相同的包，加大管理成本，可能出现同一包多版本问题。
- **锁文件保护**：保证 package.json 与锁文件（pnpm-lock）统一，防止其他开发者拉下代码后因不统一造成功能差异。

**9.1 冗余依赖治理**

按照如下顺序检查：

1. 执行 `pnpm why <package-name>`，找出项目中特定包被谁依赖，给出依赖来源。
2. 全局搜索包名，检查是否有被引入。
3. 了解包的作用，判断项目中是否存在包的引用。
4. 删除包，执行 `pnpm i` 后，分别运行、打包项目，查看是否有明显问题。

> 按顺序执行完毕后仍可能存在问题，无法完全避免，可进一步通过测试排查。

**9.2 重叠依赖治理（Monorepo 场景）**

通过人肉 + 脚本方式治理。编写脚本遍历子项目中的 `package.json`，将与根目录重叠的依赖输出：

```javascript
import fs from 'fs';
import path from 'path';
import { fileURLToPath } from 'url';
import chalk from 'chalk';

const __dirname = path.dirname(fileURLToPath(import.meta.url));

function readPackageJson(filePath) {
  try {
    const jsonData = fs.readFileSync(filePath, 'utf8');
    return JSON.parse(jsonData);
  } catch (error) {
    console.error(`读取文件失败: ${filePath}`, error);
    return null;
  }
}

function compareDependencies(rootDeps, childDeps, depType, childName) {
  const overlaps = [];
  for (const [dep, version] of Object.entries(childDeps)) {
    if (rootDeps[dep]) {
      const versionCompare = rootDeps[dep] === version;
      overlaps.push(
        `${dep}: ${chalk.blueBright(version)} (在根目录中为: ${chalk.blueBright(rootDeps[dep])}) ${versionCompare ? chalk.green('是') : chalk.red('否')}`
      );
    }
  }
  return {
    overlaps: overlaps.length > 0
      ? `${chalk.greenBright('- 重叠的', depType)}\n` + overlaps.join('\n') + '\n\n'
      : '',
  };
}

function main() {
  const rootPackageJsonPath = path.join(__dirname, 'package.json');
  const rootPackageJson = readPackageJson(rootPackageJsonPath);
  if (!rootPackageJson) {
    console.error('无法读取根目录的 package.json 文件');
    return;
  }

  console.log(chalk.bold('依赖分析报告\n'));

  const packagesDir = path.join(__dirname, 'packages');
  const childDirs = fs.readdirSync(packagesDir)
    .filter(child => fs.statSync(path.join(packagesDir, child)).isDirectory());

  for (const child of childDirs) {
    const childPackageJsonPath = path.join(packagesDir, child, 'package.json');
    const childPackageJson = readPackageJson(childPackageJsonPath);
    if (childPackageJson) {
      console.log(chalk.bold(`子项目 ${child}`));
      ['dependencies', 'devDependencies', 'peerDependencies'].forEach(depType => {
        const { overlaps } = compareDependencies(
          rootPackageJson[depType] || {},
          childPackageJson[depType] || {},
          depType,
          child
        );
        console.log(overlaps);
      });
    }
  }
}

main();
```

**执行效果示例：**

```
依赖分析报告

子项目 A
- 重叠的 dependencies
@babel/runtime-corejs3: ^7.14.0 (在根目录中为: ^7.14.0) 是

- 重叠的 devDependencies
@commitlint/cli: ^13.1.0 (在根目录中为: ^13.1.0) 是
@commitlint/config-conventional: ^13.1.0 (在根目录中为: ^13.1.0) 是

子项目 B
- 重叠的 devDependencies
typescript: ^4.4.0 (在根目录中为: ^4.3.5) 否
zx: ^4.2.0 (在根目录中为: ^4.2.0) 是
chalk: ^4.1.0 (在根目录中为: ^4.1.0) 是
```

**Monorepo 依赖管理规则：**

- 将共享的**开发时**依赖移至根目录的 `package.json`，如 jest、eslint、lint-stage。
- 对于需要特定版本以保证兼容性的依赖，考虑使用 `resolutions` 字段强制解析为特定版本。
- 为需要发包的工具、类库提供 `peerDependencies` 字段。
- 对于运行时依赖，如果所有子项目都有依赖，删除子项目中的声明，提升至根目录，同时在需要发包的工具、类库的 `peerDependencies` 中声明相关依赖。
- 发包时，通过调用脚本将目标子项目中的 `peerDependencies` 内容转移至 `dependencies` 中。

**9.3 锁文件保护**

**核心目的**：保证任何开发者在拉取代码后，执行 `pnpm i` 不会导致 pnpm-lock 发生更新。

**初步方案**

1. 限制 pnpm、node 版本。
2. 本地在 lint-stage 中新增脚本检查是否存在意外更新。
3. CI 流水线上检查是否存在意外更新。

**pnpm install 关键选项**

| 选项 | 说明 |
|------|------|
| `--frozen-lockfile` | 不生成 lockfile，如果依赖项更新是必要的则命令直接失败。CI 环境中默认开启。 |
| `--fix-lockfile` | 检查当前项目依赖关系，更新 pnpm-lock.yaml 以确保记录的包版本与 package.json 声明一致。 |
| `--lockfile-dir <dir>` | 控制 pnpm-lock.yaml 的生成路径。 |
| `--lockfile-only` | 只更新 pnpm-lock.yaml 和 package.json，不写入 node_modules 目录。 |
| `--no-frozen-lockfile` | 禁用 CI 环境中默认开启的 frozen-lockfile。 |

**锁文件检查脚本实现**

核心思路：检测 package.json 和 pnpm-lock 的依赖是否对等，使用 `--frozen-lockfile`：

```javascript
import { execSync } from 'child_process';
import { chalk } from 'zx';

try {
  execSync('pnpm install --frozen-lockfile', { stdio: 'inherit' });
  console.log(
    chalk.green('The pnpm-lock.yaml is up-to-date. No updates are needed.')
  );
} catch (error) {
  console.error(
    chalk.red(
      'Detected that pnpm-lock.yaml needs an update. Please run pnpm install and commit the updated lockfile.'
    )
  );
  process.exit(1);
}
```

基于此脚本，还可以加入 pnpm、node 版本不一致判断等额外检查。如需扩展，可考虑使用 pnpm hooks 或相关工具（如 rush）。
